# Do Tsinghua Homework

将作业实现、报告写作、用户修改确认和 PDF 导出串成一个流程。这是用户个人的工作方式和写作偏好，不是清华大学的统一格式规范。当前作业及用户的明确要求优先。

## 默认流程：先 Markdown，再确认，再 PDF

1. 先读取当前题目、实验文档、已有报告及相关源码。按题目完成必要的实现、实际运行、数据分析和验证，再撰写报告。写作前读取 [写作风格](references/writing-style.md)。作业只要求阅读或回答问题时，按题目范围完成，不额外增加实验。
2. **第一版报告必须保存为可编辑的 .md 文件，并返回该文件的可点击链接。** 图片用稳定路径引用，默认相对于 Markdown 所在目录。核对题目覆盖、代码依据、真实结果及图片路径后，交付 Markdown，说明它供用户修改和确认。此时结束报告写作阶段，等待用户；不要自动生成 PDF、先做 PDF 再补 Markdown，或将报告替换成只有聊天正文的交付。
3. 用户提出修改时，重新读取其最新保存的 Markdown，在同一文件内修改，保留姓名学号、用户改写、删除的内容、代码和图片路径。返回更新后的 Markdown，继续保留确认环节。仅要求改正文不等于同意导出 PDF。
4. 用户明确表示“确认，可以转 PDF”“按最新 MD 导出”或直接要求将现有 Markdown 转成 PDF 后，读取 [PDF 导出](references/pdf-export.md)，使用本技能的 scripts/export_pdf.py 导出。**导出前重新读取磁盘上的最新 Markdown，以该文件为正文唯一来源。** 不从旧版生成脚本、旧结果模板或聊天草稿恢复正文，也不在导出过程中改写内容。
5. 检查 PDF 的每页预览，修正排版问题，保留可编辑的 Markdown，交付 PDF。若题目需要提交压缩包，再将确认后的报告与题目要求的代码、README、检查结果打包，按课程要求排除原始数据、权重和无关文件。

## 确认边界与不同入口

- “帮我做作业”“写报告”默认先交付 Markdown；即使题目最终要求 PDF，也要保留用户修改确认的环节。
- 用户直接要求导出已有 Markdown，或明确要求本次跳过确认、直接交付 PDF，已经授权相应导出，无需重复询问。仍需以最新文件为准。
- 用户仅确认正文但未提出导出要求时，保留 Markdown；“确认，转 PDF”即可进入导出阶段，不增加第二次确认。
- 用户在已有 PDF 后修改 Markdown，按新指令判断是否同时重导出；仅改正文时先交付修改后的 Markdown。
- 写作阶段等待确认的是报告导出。授权范围内的代码实现、实验、结果保存和检查应完成，不因报告待确认而留下必要工作。

## 作业依据与文件维护

- 当前题目决定结构、实验数量、代码修改范围和提交内容。明确区分必做项、已验证项和可选加分项；保持实现与真实实验一致，不虚构截图、成绩、个人经历或操作过程。
- 已有报告先读再改，按授权范围作局部或增量编辑。正文采用简洁、自然的中文段落；必要题号和标题保留，详细风格见 writing-style.md。
- 分析用明确的陈述句，直接写出有源码或实验依据的结果和原因。删去“应结合……判断”“不能只凭……评价”等泛泛提醒，避免为过度严谨追加无关限制或保留意见，也不自动追加“超参数选择依据验证集，测试指标只用于报告最终表现”这类实验流程自证句。必要条件简短融入结论，具体要求见 writing-style.md。
- 姓名学号缺失时留空或询问，不猜测。用户确认后的报告和包名使用其提供的信息。
- 转 PDF 只处理排版。中文宋体正文、黑体标题，嵌入真实字体；图片等比缩放，检查分页、缺字、溢出和字段可读性。普通 Markdown 报告复用随附脚本，不为每次导出另写转换程序；遇到复杂公式或不支持的格式时按实际需要选工具，继续保留 Markdown 和确认边界。
