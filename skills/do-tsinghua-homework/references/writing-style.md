# Writer 清华 Report

这是用户个人的报告写作风格，不是清华大学的统一格式规范。目标是写成逻辑清楚、技术准确的学生作业：把问题说明白，保留关键依据，减少装饰性内容。用户当前的明确要求优先于本技能。

## 写作方式

- 使用正常、自然的书面语。避免刻意口语化、夸张的学术表达、宣传语和反复总结。
- 用明确、确定的陈述句写清实际行为、结果和原因。已由源码或实验支持的结论直接说明，不用“可能、也许、需要进一步判断”等泛泛措辞弱化表述。
- 不写“应结合……判断”“不能只凭……评价”“不能据此认为……”这类面向读者的泛化提醒，也不在分析末尾追加为了显得严谨而写的评价原则、保留意见或方法建议。把篇幅用于当前实验具体发生了什么、为什么会发生。
- 不自动追加“超参数选择依据验证集，测试指标只用于报告最终表现”这类实验规范或流程自证句，也不反复解释训练集、验证集、测试集各自应承担什么职责。正文直接说明采用的参数、实际结果和选择原因；题目专门问到数据划分、选择流程或实验方法时，在对应位置具体回答，不将其作为每段结尾的固定说明。
- 必要条件应直接融入事实陈述，例如“训练时随机屏蔽特征，测试时使用完整输出”。题目要求或影响结论的实质条件用一句话交代；与当前结果无关的限制不展开。确定的语气建立在真实依据上，缺少依据时先核查，不把未验证内容写成事实。
- 以连贯段落为主，直接说明对象、代码行为、操作流程和结果。少用“首先、其次、最后、综上所述、值得注意的是”等连接词；需要表达先后或因果时自然写清关系。
- 详略以题目为准。正文集中说明主要实验的基本流程、实现思路和结果，适当展开核心代码的处理过程。简洁不能变成省略代码依据或只给一句结论。
- 不附加与题目和主要实现无关的澄清、限定、免责声明或后续阶段提醒。思考题说明概念、原因和例子后即可结束，不自动追加当前框架的限制或适用范围。题目直接要求的边界条件以及理解实际结果必需的信息仍应保留。
- 优先用正向陈述说明实际作用。减少“不是……而是……”“没有……”“不会……”等无关对比或否定式补充。涉及正确性或实质限制时仍须如实说明，可以换成直接说明实际行为的句子。
- 正文中的函数名、寄存器、地址、文件名直接写出，不用行内反引号、单引号、双引号或加粗逐个框住。引用原代码时使用代码块，保留原代码里的引号、操作符和语法。
- 正文介绍实现时优先使用类名、函数名或简短文件名，避免罗列完整目录路径。题目明确要求代码位置或同名文件需要区分时，再给出必要路径。
- 将篇幅用于主要实验内容，多引用自己补写的代表性代码，并紧接着说明输入、处理过程、输出及其与前后步骤的关系。用具体代码解释关键选择，避免只罗列改动文件或堆砌整段源码。引用框架或参考代码时说明其作用与新增部分。
- 环境配置和测试支撑只保留与实验结论有关的内容，省略工具版本清单、目录布置和运行适配细节。思考题要求的架构、编译参数和真实结果仍需说明；影响结果解释的适配用简短说明交代。
- 不虚构个人经历、操作、结果或理解程度。自然风格通过具体内容和简洁表达实现。

表达示例：

删去：“应结合验证曲线判断正则化收益，不能只凭较低训练准确率评价效果。”

也删去：“超参数选择依据验证集，测试指标只用于报告最终表现。”

结合已有实验结果直接写：“去掉 Dropout 后，训练准确率由 68.34% 升至 81.22%，验证损失由 1.3586 升至 1.5582。Dropout 减轻了后期过拟合。”示例数值仅用于说明写法，实际报告必须使用当前实验的数据。

## 结构与依据

按照当前题目和用户已有报告组织内容，使用必要的标题或题号即可。避免自动添加摘要、关键词、背景、意义、总结、展望等模板章节，也避免每段再加小标题。表格和图仅在明显有助于理解时使用，图尽量简单。

代码阅读报告通常先说明整体结构，再引用关键源码，紧接着解释它完成的操作和与其他部分的关系。思考题按原题顺序回答；题目要求结合代码或指出位置时，必须引用实际源码并通过函数、类、标签或分支说明位置，必要时补充文件名。选择能支持结论的短片段，长函数可以分段摘录，删节处明确说明。概括性的伪代码要标明是简化表示，不能当作原代码。

示例表达：

以下代码位于 shell.S 的 .OP_G：

```asm
li a0, SIG_TIMERSET
jal WRITE_SERIAL
```

程序将开始信号放入 a0，通过 WRITE_SERIAL 发送给 Term。Term 收到信号后记录开始时间。

实验结果结合真实截图或输出说明。涉及进制、地址、数据宽度时，交代足以核验结果的关系，例如低位和高位怎样组成最终数值。截图用于证明运行情况，正文用少量文字解释操作和结果。

## 编辑和检查

编辑前重新读取用户最新保存的文件，保留已有姓名学号、正文、代码、图片路径和排版选择，只修改授权范围。用户要求直接写入已有报告时，在该文件内完成修改。

先读题目、实验文档和相关源码，再写分析。检查报告时区分课程明确要求、已经证实的完成项和可选改进，不能把自己的排版偏好变成额外作业要求。查看图片内容后再判断结果是否正确；区分预期结果、实际运行结果和未验证内容。

交付前检查题目覆盖情况、代码引用与解释是否一致、图片引用是否存在，以及是否保留用户最新修改。反馈直接说明已做的修改和确实需要补充的内容。
